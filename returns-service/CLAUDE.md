# returns-service — QAYDAO Returns (isolated sidecar)

## ما هي الخدمة
خدمة FastAPI مستقلة لإدارة طلبات إرجاع العملاء. تعمل داخل Docker كـ **sidecar منفصل تماماً عن Chatwoot**.
- الكود: ملف واحد `app/app.py`
- قاعدة بيانات خاصة `returns` (حاوية `returns_db`, postgres 16) — **لا علاقة لها بقاعدة Chatwoot إطلاقاً**
- المنفذ الداخلي: `127.0.0.1:8091`
- تخزن `conversation_id` كمرجع فضفاض فقط (لا FK إلى Chatwoot)

## الحاويات
- `returns_service` — تطبيق FastAPI (يُعاد بناؤه عند تغيير الكود)
- `returns_db` — postgres (لا يُعاد إنشاؤها عند تحديث الكود)

⚠️ تنبيه تشغيلي: اسم مشروع compose قد يتعارض (`returns_service` مقابل `returns-service`).
لإعادة نشر الكود بأمان دون لمس الـ DB:
```
docker compose up -d --build returns_service      # يبني الصورة
docker rm -f returns_service                       # يحذف حاوية الخدمة فقط (ليس returns_db)
docker compose up -d --no-deps returns_service     # يعيد الإنشاء من الصورة الجديدة
```
تحقق دائماً: `docker exec returns_service grep -c "<دالة جديدة>" /app/app.py` قبل إعلان النجاح.

## الأدوار والصلاحيات (مفروضة server-side في `allowed_statuses_for`)
- **المحاسبة** `financial@qaydao.com` + **الإدارة** `rami@qaydao.com`: الحالات المالية فقط `will, doing, done, rejected`.
- **النذير (مدير المشتريات)** `pr@qaydao.com`: `done_salla` **فقط**.
- لا تداخل: أي محاولة لإرسال حالة خارج نطاق الدور ترجع **403**.
- تبويب "تم الإرجاع في سلة" ظاهر للجميع كمتابعة، لكن **زر** الإجراء يظهر حسب `canStatus()` + حالة الطلب (انظر قسم "إغلاق الأزرار حسب الحالة").

## إغلاق أزرار الحالات حسب الحالة الحالية (frontend + server — جذري)
مفروض في طبقتين: الواجهة `visibleActions(x)` داخل `ACCOUNTANT_HTML`، والسيرفر في `set_status` (PATCH `/returns/api/requests/{id}/status`). لا يُعتمد على إخفاء الأزرار وحده.

**المحاسب (financial/rami):**
- `new` ⇒ الأزرار الأربعة: سيتم / جاري / تم / مرفوض.
- `will` أو `doing` ⇒ زر **تم الإرجاع** فقط (لا رجوع إلى سيتم/جاري/مرفوض). شرط إيصال التحويل عند `done` كما هو.
- `done` ⇒ لا أزرار، بطاقة قراءة-فقط خضراء "منتهٍ مالياً".
- `rejected` ⇒ لا أزرار، بطاقة `locked` حمراء (نهائي).
- `done_salla` ⇒ الأزرار الأربعة للمحاسب، **بدون** زر "تم الإرجاع في سلة" (خارج صلاحيته أصلاً).

**النذير (pr):** زر **تم الإرجاع في سلة** فقط، ويظهر **حصراً** على الحالات `new` / `will` / `doing`. لا يظهر على `done_salla` / `done` / `rejected`.

**قيود السيرفر (409 عند المخالفة):**
- `done` ⇒ يرفض أي تغيير حالة.
- `rejected` ⇒ يرفض أي تغيير حالة (نهائي).
- `will` / `doing` ⇒ لا يقبل من حالات المحاسب إلا `done` فقط (مسار النذير `done_salla` مستقل غير خاضع لهذا القيد).
- تجاوز الدور (محاسب↔نذير) ⇒ **403** كما هو عبر `allowed_statuses_for`.

## آلية "تم التواصل" للطلبات المرفوضة
عند رفض المحاسب لطلب، يظهر تنبيه أحمر أعلى صفحة فريق خدمة العملاء (`/returns/team-requests`).
- الموظف يضغط زر **"تم التواصل"** بجانب الطلب المرفوض بعد أن يتواصل مع المحاسب.
- ذلك يستدعي `POST /returns/api/requests/{id}/contacted` الذي يضبط العمود `contacted_at` فقط.
- **حالة الطلب تبقى `rejected`** — لا يتغير أي منطق مالي.
- التنبيه الأحمر يحسب **فقط** الطلبات المرفوضة التي `contacted_at IS NULL`.
  - طلبان مرفوضان + التواصل مع واحد ⇒ التنبيه يعرض 1.
  - التواصل مع الكل ⇒ التنبيه يختفي بالكامل.
- الطلب المتواصَل معه يظهر بشارة هادئة **"مرفوض — تم التواصل"** (رمادية، لا حمراء).

## تعريب الحالات
جميع الحالات تُعرض بالعربية في الواجهة. `done_salla` تظهر للمستخدمين باسم **"تم الإرجاع في سلة"** في:
- backend `STATUS_LABELS` (يغذّي `status_label`)
- صفحة المحاسب `SL`
- صفحة فريق خدمة العملاء `SL` + badge `b-done_salla`
الكلمة الخام `done_salla` لا تظهر للمستخدمين في أي مكان.

## طريقة الاسترداد (refund method)
نموذج خدمة العملاء لم يعد يطلب البيانات البنكية مباشرة. يختار الموظف **طريقة الاسترداد** أولاً،
والحقول التالية تتبدّل حسب الاختيار.

| القيمة المخزَّنة | ما يراه المستخدم | الحقول الظاهرة/الإلزامية |
|---|---|---|
| `tabby` | تابي | **رقم / مرجع تابي** فقط |
| `tamara` | تمارا | **رقم / مرجع تمارا** فقط |
| `madfooat` | مدفوع | **رقم / مرجع مدفوع** فقط |
| `bank_account` | الحساب البنكي | اسم البنك + الحساب البنكي + الآيبان + **ملف/صورة الحساب البنكي** |

- مع تابي/تمارا/مدفوع **تُخفى** حقول البنك/الحساب/الآيبان تماماً، **ولا** يُطلب ملف الحساب البنكي
  (كان إلزامياً للجميع قبل هذه الميزة — أصبح إلزامياً للطريقة البنكية فقط، لأنه بلا معنى مع البقية).
- **تحقق الآيبان لم يتغيّر:** `^SA\d{22}$` (24 خانة)، ويسري على الطريقة البنكية فقط.
- **التحقق مفروض في طبقتين:** الواجهة (`toggleRefund` + `required` الديناميكي في `save()`)
  والسيرفر `validate_refund()` الذي يرجع **422** برسالة عربية. لا يُعتمد على إخفاء الحقول وحده.
- **تطبيع عند الحفظ:** كل طريقة تحتفظ بحقولها فقط — طلب تابي لا يخزّن أي بيانات بنكية، والعكس.

**العرض:**
- **صفحة المحاسب** `/accountant-returns` — دالة `refundRows(x)` داخل `ACCOUNTANT_HTML`:
  صف «طريقة الاسترداد» دائماً، ثم إمّا «رقم / مرجع <الطريقة>» **مع زر نسخ**،
  أو البنك/الحساب/الآيبان مع أزرار النسخ كما كانت.
- **النذير** — نفس البطاقة ونفس الصفحة ⇒ يرى طريقة الاسترداد للقراءة. **صلاحياته لم تتغيّر** (`done_salla` فقط).
- **صفحة فريق خدمة العملاء** `/returns/team-requests` — عمود «طريقة الاسترداد» فقط.
  الرقم/المرجع والبيانات البنكية **تبقى مستبعدة** من `/returns/api/team-requests` (سياسة الخصوصية القائمة).

**السجلات القديمة:** `refund_method IS NULL` تُعرض كـ«الحساب البنكي» عبر `refund_method_label`
في `row_to_dict` — عرضاً فقط، لا يُكتب شيء إلى قاعدة البيانات.

## قاعدة البيانات
أعمدة متعلقة بهذه الميزات (كلها `NULL`-able وإضافية — لا تكسر أي منطق قائم):
- `contacted_at TIMESTAMPTZ NULL` — وقت تأكيد الموظف للتواصل. `NULL` = لم يتواصل.
- `refund_method TEXT NULL` — `tabby` / `tamara` / `madfooat` / `bank_account`.
- `refund_reference TEXT NULL` — الرقم/المرجع لتابي/تمارا/مدفوع (فارغ للطريقة البنكية).

أُضيفت بـ`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` على قاعدة **`returns` فقط**، وموثّقة أيضاً في
`schema.sql` لتوافق إعادة التهيئة. **قاعدة Chatwoot لم تُمَس إطلاقاً.**

## شريط "طلب منتج جديد" (صفحة المحاسب فقط — عرض بصري)
- **المعيار:** إذا كان `original_order_at` (تاريخ طلب المنتجات الأصلي) خلال **3 أيام أو أقل** من تاريخ اليوم، يظهر شريط أخضر **"طلب منتج جديد"** أعلى بطاقة الطلب في صفحة المحاسب `/accountant-returns`.
- **الغرض:** يعرف المحاسب مباشرة أن الطلب حديث فيأخذه كأولوية أعلى عند الإرجاع المالي.
- **الحساب:** client-side فقط في دالة `isRecentOrder()` داخل `ACCOUNTANT_HTML` — `floor((اليوم − original_order_at) بالأيام) ما بين 0 و3`. اليوم/أمس/قبل يومين/قبل 3 ⇒ يظهر؛ قبل 4+ ⇒ لا يظهر.
- **بدون عمود جديد** — يُحسب من الحقل الموجود `original_order_at`. لا يغيّر الحالة ولا الصلاحيات ولا قاعدة البيانات.
- **معزول تماماً:** موجود حصراً في كتلة `ACCOUNTANT_HTML` (CSS `.ribbon-new`/`.card.is-new` + دالة `card()` الخاصة بالمحاسب). صفحة فريق خدمة العملاء `/returns/team-requests` لا تتأثر إطلاقاً.
- تم الاختبار بطلبين تجريبيين (حديث قبل يومين ⇒ ظهر، قديم قبل 5 أيام ⇒ لم يظهر) وتم تنظيفهما بالكامل بعد الاختبار.

## تنبيه توفر الصنف في مستودع السعودية (stock-hint) — 2026-09-06

### الغرض
قبل صرف أي مبلغ إرجاع، يعرف الموظف/المحاسب/المشتريات أن الصنف موجود **فعلياً**
في مستودع السعودية — فيُعرض على العميل **الاستبدال أو التسليم الفوري** بدل الاسترجاع.
(طلب رامي: «تنبيه للموظف عند طلب رجيع لتوضيح أنها متوفرة في المستودع».)

### المعمارية — طبقتان، بلا تكرار حساب
```
نموذج Chatwoot / بطاقة المحاسب / صفحة الفريق
        ↓  GET /returns/api/stock-hint?order_number=X   (بلا سر — داخل الشبكة)
returns-service  (app.py)
        ↓  GET https://cn.qaydao.com/api/internal/order-stock   (Bearer token)
CN-Ops  (backend/app/api/internal.py)
        ↓
warehouse_match.stock_for_codes  ← مصدر الحقيقة الوحيد
```
**الحساب لا يُكرَّر هنا إطلاقاً.** نفس الدالة تغذّي الشارة الحمراء في شاشة طلبات
CN-Ops وبوابة اعتماد الشراء ⇒ رقم واحد لا يتناقض بين الشاشات.
`المتاح = (الوارد − المنصرف) − الحجوزات النشطة` ، والمطابقة على `cn_code` **أو** `qd_code`.

### الأسطح الأربعة
| السطح | الشكل | من يراه | متى |
|---|---|---|---|
| نموذج الإرجاع (`injection/qaydao-returns-tab.js`) | لوحة كهرمانية `#q_stock` | خدمة العملاء | عند مغادرة حقل `q_order` — قبل فتح الطلب أصلاً |
| بطاقة الطلب (`ACCOUNTANT_HTML`) | شريط `.ribbon-stock` فوق البطاقة | المحاسب **والنذير** (نفس البطاقة) | قبل صرف المبلغ |

| CN-Ops `/dashboard/orders` (قائم سابقاً) | شارة حمراء + بوابة تأكيد | المشتريات | قبل اعتماد الشراء |

### قاعدة الإخفاء (رامي 2026-09-06)
الطلب بحالة **`done`** أُرجع مبلغه للعميل فعلاً ⇒ **لا يظهر التنبيه إطلاقاً** على
الأسطح الثلاثة. مطبَّقة في `card()` و`row()` كشرط قبل إنشاء عنصر المكان
(`stkslot` / `stkslotT`) — لا يُرسل نداء أصلاً.
`done_salla` **يُبقى عليه التنبيه**: المحاسب لا يزال يملك أزراره الأربعة، أي المبلغ لم يُصرف بعد.

### مبادئ التصميم (لا تُخالَف عند أي تعديل لاحق)
- **غير معطِّل**: يُحمَّل بعد رسم الصفحة/البطاقات، ولا يمنع حفظ طلب الإرجاع أبداً. معلومة لا بوابة.
- **صامت عند الفشل**: أي فشل (شبكة/مهلة/401) ⇒ `available:false` ولا شيء يظهر. لا رسالة خطأ للموظف.
- **السر لا يصل المتصفح**: `CNOPS_SERVICE_TOKEN` يُستعمل server-side فقط داخل `returns_service`.
- **بلا اعتمادية جديدة**: `urllib` القياسية داخل `asyncio.to_thread` (لا httpx). مهلة 3 ثوانٍ، كاش 120 ثانية.
- **بلا PII**: النقطة الداخلية لا ترجع اسم عميل ولا مبالغ — أكواد وكميات ومواقع فقط.
- **صفر تغيير** في قاعدة `returns` (لا أعمدة جديدة) ولا الحالات ولا الصلاحيات ولا منطق المحاسب.

### الإعدادات
`returns-service/.env` (مستثنى من Git) + مثبّتة صراحةً في `docker-compose.yml`
تحت `environment:` حتى لا تسقط الميزة صامتة إن أُعيد إنشاء الحاوية:
```
CNOPS_STOCK_URL=https://cn.qaydao.com/api/internal/order-stock
CNOPS_SERVICE_TOKEN=<نفس RETURNS_SERVICE_TOKEN في /opt/cn-qaydao-ops/.env>
```
⚠️ **درس تشغيلي 2026-09-06:** `docker restart` **لا** يعيد قراءة `env_file` —
لزم `docker compose up -d --no-deps --force-recreate`. لذلك ثُبِّتت المتغيرات في
`environment:` كتحصين دائم (اختُبر: بعد `docker restart` بقيت الميزة تعمل).

### المطابقة بالاسم عند غياب cn_code (2026-09-06 — قرار رامي)
الطلبات قبل يوليو 2026 لم يكن الجسر يختم فيها `cn_code`، **لكن الكود مكتوب فعلياً
داخل حقل اسم البند** (مثل `name="JB-S105"` و`cn_code` فارغ). لذلك تستخرج
`internal.py` رموزاً مرشّحة من الاسم والمقاس عند غياب `cn_code`.

**ضابط منع الإيجابيات الكاذبة — لا يُلغى:** المطابقة تتم داخل
`stock_for_codes` على `cn_code`/`qd_code` لأصناف المستودع **فقط، لا على أسمائها**،
والرمز ≥4 محارف وليس رقماً خالصاً. قياس فعلي: بلا هذا الضابط ظهرت **54** نتيجة
أغلبها كاذب (`CHAIR` · `DESK` · `WHITE` طابقت أسماء أصناف)، ومعه **12** صحيحة.

الاستجابة تحمل `code_source` (`cn_code` أو `name`) و`declared_cn_code`، فيبقى
أصل كل مطابقة معروفاً ولا تختلط المستنتَجة بالمصرَّحة.

**الأثر:** من 86 مرتجعاً لم يُصرف مبلغه، انتقل التنبيه من **0 إلى 12**.

### قاعدة العمل عند ظهور التنبيه (رامي 2026-09-06)
> «هذه ليست أخطاء — يجب تنبيه المحاسب والمشتريات لضمان شحنه للعميل بعد التأكد من العميل.»

التنبيه ليس تحذير خطأ بل **فرصة**: يُراجَع العميل أولاً، وإن وافق **يُشحن له الصنف
من المستودع** بدل صرف المبلغ. لذلك نص التنبيه: «لا تصرف المبلغ قبل مراجعة العميل
— تأكّد من العميل ثم اشحن له الصنف من المستودع بدل الاسترجاع».
